# ugas

## 1.0.0-draft.6

### Patch Changes

- 5d9737c: [Fixed] `ugas-schema-author` simulator — a bound that references another attribute now resolves against that attribute's **clamped** Current Value, and clamp rules are validated at parse time. Also adds a §5.4 spec clarification for the semantics this depends on.

  **A dependent attribute could exceed the bound it references, and the excess was written permanently to the Base Value.** Reference bounds resolved through the unclamped pipeline result, so with `MaxHealth` capped at `200` and carrying a `+500` buff, `Health` bounded by `max: MaxHealth` was permitted up to `700` — displayed `Health` could exceed displayed `MaxHealth`, the exact invariant the bound exists to enforce. Worse, base clamping used the same resolution: an `Instant` write landing while the ceiling was inflated stored `Health.base = 700` permanently. The buff expiring did not undo it and read-time clamping concealed it, but the Base Value is the persisted component (§5.2), so it survived save/load and resurfaced the moment `MaxHealth` legitimately rose. §5.4 rule 1 says the referenced attribute's Current Value is the bound, and §5.3 places clamping inside that definition (pipeline step 7), so the clamped value is the correct bound.

  **`min` and `max` were applied in the wrong order.** §5.3's formula is `max(V_min, min(V_max, x))`, so `min` wins where a resolved `min` exceeds a resolved `max`. Both the display and base-write paths applied `min` first and `max` second, giving `max` — `30` where the formula gives `50`. Reachable in practice because dynamic bounds let a `min` reference rise above a static `max`.

  Both are fixed by consolidating clamping into a single definition of a Current Value used by the display path and by bound resolution alike, rather than the three partly-divergent implementations that existed before. The unclamped pipeline helper is renamed to `compute_unclamped` — a function named for the Current Value while omitting the clamp is what allowed these to diverge.

  **Clamp rules are now validated when parsed**, in the same fail-loudly spirit as the effect validation: a rule keyed on an undeclared attribute, and a bound referencing one, are rejected instead of silently meaning "no bound" (a `max: MaxHelth` typo previously removed the ceiling with no signal). Circular bound references — including a self-reference — are rejected with the full cycle path, e.g. `Health -> MaxHealth -> Health`. §5.4 already forbade them; they previously produced a wrong number rather than an error only because bound resolution stopped at the first hop, and resolving against clamped values makes a cycle genuinely unresolvable. **This makes such configs breaking**: they ran before and now exit with an error.

  Malformed clamp shapes are reported rather than raising a traceback: a `clamping` block that is not a mapping, a rule whose value is not a mapping (including an empty `Health:` with no bounds, which YAML reads as null), a bound that is neither a number nor an attribute name, and a key that is not a string at all (YAML reads `1:` as an int and a bare `no:` as False). A boolean bound is rejected too — `bool` is an `int` subclass, so `max: true` would otherwise have become a silent ceiling of `1.0`.

  Unknown keys inside a rule are also rejected, with a hint when they look like a case mismatch. This closes a real trap: the spec's §5.4 examples write `Min:`/`Max:` capitalised, while this config format is lowercase, so a copied example previously parsed to _no bounds at all_ with no signal — an attribute declared with `max: 100` and written as `Max: 100` simply stayed unbounded.

  Base values written in one batch are clamped in dependency order — a referenced attribute before its dependents — with authored modifier order as the tiebreak among independent attributes. Clamping a referenced attribute's base changes its clamped Current Value, so interdependent attributes give a different answer depending on the order; the reference graph is acyclic once cycles are rejected, which makes dependency order the unique result.

  [Changed] Spec §5.4 — states that a reference bound resolves against the referenced attribute's _clamped_ Current Value, with the `MaxHealth` example; notes that such a bound is temporary when the referenced attribute's modifiers are, so an `Instant` base write during a temporary reduction is clamped to the reduced bound and does not recover; and records that `Min` wins when a resolved `Min` exceeds a resolved `Max`, which previously had to be inferred from the nesting of the §5.3 formula.

  Adds `tests/test_simulate.py` — 56 standalone regression checks over the clamping behaviour this change touches: bound resolution, base-value writes, dependency and transitive ordering, `min`/`max` precedence, cycle and malformed-config rejection, and the documented example config.

  The suite is checked by mutation rather than by assertion count, because several natural-looking assertions here cannot fail: read-time clamping hides the Base Value, so a display assertion passes whether the base was written correctly or not. Of 25 single-behaviour mutations — dropping _or widening_ the clamp call at each of the three sites that write a Base Value, dropping either clamp, swapping `min`/`max`, reintroducing the unclamped-bound bug, returning no bound, reducing transitive ordering to direct references, writing the clamped current into the base instead of the base, dropping the t=0 normalisation, breaking the cycle walk so it rejects a legal diamond, weakening the case-mismatch hint, and disabling each validation — 24 are caught. The survivor replaces the ordering tiebreak with alphabetical, which is behaviourally equivalent: attributes with no reference relationship cannot affect each other's bounds, so their relative order is unobservable.

- c240e40: [Fixed] Schemas, spec, and the `ugas-schema-author` skill — swept out a family of stale descriptions that contradicted the normative modifier pipeline (§5.3). Three classes of defect: two described `Multiply` as taking a raw _factor_ rather than the signed bonus the pipeline actually applies, and one described channel aggregation backwards.

  **Inverted `Multiply` convention.** The `Modifier.Operation` description in `gameplay_effect.json`/`.yaml` told consumers to use a "reciprocal magnitude (e.g. `0.5`)" in place of a Divide operation. `Multiply` magnitudes are signed bonuses aggregated as `(1 + Σm)`, so `0.5` is a _+50% bonus_ — a consumer following the description to halve an attribute would have increased it by 50%, silently and without a validation error. §9.4.1 already specified `−0.5`. Both schema copies now state the signed-bonus convention with that example, and note that on an `Instant` effect a `Multiply` scales the Base Value by `(1 + magnitude)` with no channel grouping, so magnitude `0` is the identity (§5.2).

  **`Channel` omission described backwards.** Both schemas said a modifier with no `Channel` "defaults to the global channel". The normative rule (§5.3, and §9.4's own doc comment) is the opposite: it becomes its own implicit _singleton_, contributing independently. The distinction is material — two channel-less `+0.5` modifiers yield ×2.25, not ×2.0. Also corrected the cross-reference from §16.3 (the ARPG case study) to §5.3 Channel Aggregation.

  **Stale 8-step pipeline numbering.** The schema descriptions and the §9.4 TypeScript doc comment numbered `Multiply` 6, `AddPost` 7, `Override` 8 — a fossil of a defunct formulation with a separate "additive percentage" stage. The normative §5.3 Order of Operations and the §9.4.1 table both say 4/5/6; every source now agrees. The §5.3 worked example was itself still built on that defunct model (inputs labelled "Additive Percentage" — never an operation — and "Multiplicative 1: 1.5×" as raw factors) and has been rewritten to demonstrate real channel aggregation, arriving at the same 487.5. The `SPEC.adoc` notation glossary no longer defines an unused `p` "percentage modifier magnitude", and `m` is now described as a signed bonus.

  The `Operation` enum values were correct throughout and are unchanged; no gameplay data needed edits (the genre packs already used signed magnitudes).

  Also fixes the bundled `ugas-schema-author` simulator, which implemented the stale model in runnable code: the modifier pipeline multiplied raw magnitudes (`result *= m`) with no channel grouping, and `apply_instant_modifiers` did `base_value *= magnitude`, so an Instant `Multiply` of `0` zeroed the attribute instead of acting as the identity. It now groups by `Channel`, applies `(1 + Σm)` per channel, and treats channel-less modifiers as singletons. The skill's `SKILL.md` pipeline summary, `references/schemas.md`, `references/simulation-config.md` (including an example that authored `value: 1.5` for "50% more armor"), and audit-checklist guidance are corrected to match.

  Two further simulator conformance bugs, found while reviewing the above, are fixed in the same pass:

  - **Stacked effects expired incorrectly.** Modifier ownership was tracked by the list index recorded at application time, and the function meant to re-sync those indices after a removal was an empty stub. Once any effect expired, every other effect's recorded indices were stale: with three timed `Add` effects on one attribute, one expiry removed nothing and another removed the wrong effect's modifier, leaving the attribute permanently wrong. Entries are now tagged with their owning effect's name and removal filters on that name, so stacked effects may expire in any order. `Override` is likewise owner-tracked, so an expiring override correctly falls back to a still-active one (§5.3 LIFO tie-break).
  - **Periodic `Multiply` was written to the Base Value every tick.** Periodic executions routed through the Instant path, applying every operation to the base and compounding the result each tick — so a periodic `Multiply` authored as `+0.10` drove an attribute 100 → 10 → 1 → 0.1 toward zero (the released code multiplied by the raw magnitude), permanently and surviving expiry. §5.2 requires periodic executions to apply only `Add` / `AddPost` / `Override` to the base, precisely to avoid that compounding. A periodic durational effect now writes only those three to the Base Value on each execution, while its `Multiply` modifiers are registered as Current-Value modifiers for the effect's lifetime and withdrawn on expiry — so the percentage applies for as long as the effect is active, without accumulating and without being dropped.

  Finally, drops a `Divide` modifier reference in §5.2 (and in the pending Instant-Multiply changeset) that contradicted §9.4.1's "there is no `Divide` operation", repairs a stray blank line that broke the §9.4 doc comment mid-list, and updates the `docs-site` landing-page formula, which still rendered the defunct pipeline with an "additive %" stage and a raw-factor "true mult" term.

- 8ff6e1c: [Fixed] `ugas-schema-author` simulator — clamp-bound reference graphs now scale to any legal shape, and a typo in a config key is an error rather than a silently substituted default. Resolves the follow-ups filed while reviewing the clamped-bound change in this same release.

  **Bound references resolve iteratively, at any depth or width.** Attribute-reference bounds (`max: MaxHealth`) resolve against the referenced attribute's _clamped_ Current Value, which makes resolution a walk over the reference graph rather than a single hop. That walk is iterative and memoised per read: a chain of a thousand references, or a lattice in which many attributes reference a shared set, resolves in near-linear time on a bounded stack. Written recursively — the obvious shape, given §5.4's recursive definition — that walk would raise an uncaught `RecursionError` past roughly five hundred links, and would enumerate reference _paths_ rather than _nodes_, which is exponential: measured on a recursive draft, a 20-level lattice would take about 13 seconds and a 30-level one would not finish, with nothing rejecting either. Both shapes are acyclic and therefore legal, so the cycle rejection would not cover them. The parse-time cycle check is iterative for the same reasons, sharing one visited set across every rule so accepting a wide lattice is linear too, and it still reports the full cycle path. Batch base-clamping orders its writes with a topological sort rather than rescanning for a ready attribute; the rescan it replaces — introduced alongside the ordering guarantee in this same release — would have been cubic in the number of attributes written, some 6 seconds for a thousand, and would otherwise have become the next bottleneck. Deliberately _not_ added: a depth or size limit. Nothing recurses on any config-dependent path, so a limit would reject configs the spec calls legal and that resolve in milliseconds.

  **Unknown config keys are rejected at every level.** An unknown key previously meant "take the default", which is the silent-typo class this simulator has been closing progressively: `execute_on_aplication: true` left `execute_on_application` at `false`, so the effect never executed on application while the run still reported it applied — a plausible-looking but wrong curve, with no signal. The same hole existed at the top level, where `efects:` yielded an empty effect list and a flat trace that reads as "your design does nothing"; inside a modifier; and inside the `simulation` block, where `timestap:` silently reverted to the default timestep and changed the whole x-axis. Every mapping the script reads keys out of now has a closed key set.

  The messages name the likely cause rather than only the symptom, because the common trigger is copy-paste rather than mistyping: `schemas/gameplay_effect.json` and the genre packs are PascalCase (`DurationPolicy`, `Attribute`, `Magnitude`) and carry fields this simplified format does not model (`Priority`, `Executions`, `GrantedTags`, …), so a config adapted from an entity file arrives with every key unknown. A casing variant of a real key is reported as such, `Magnitude` is pointed at `value`, and spec-only fields are reported as unsupported rather than misspelled. A plain misspelling gets no hint — only the expected-key list.

  Malformed shapes now produce a message and exit `2` where they previously raised a traceback and exit `1`: an `effects` block that is not a list, an effect or modifier that is not a mapping, a `modifiers` block that is not a list, a non-mapping `attributes` block including a present-but-empty one, a non-string attribute name, a non-numeric initial value, a non-mapping `simulation` block, and an empty config file — which YAML loads as `None`, and which used to fail while reading the `simulation` block, outside the handler that turns a config error into a message. Booleans are rejected wherever a number is required, here as elsewhere, since `bool` is an `int` subclass and `float(True)` is `1.0`, so a YAML `Health: yes` would otherwise become an attribute worth one.

  Two related traceback paths are closed with them, both reachable from an ordinary typo. A `timestep` of `0` divided by zero while computing the step count — the same never-advances class as `period: 0`, which was already rejected — so `timestep` and `--timestep` are now required to be positive and `duration` non-negative. And because `0` is falsy, `--duration 0` and `--timestep 0` fell through to the config value, silently running the full simulation the flag was meant to shorten; the flags now test for an explicit value rather than a truthy one. **The new rejections are breaking**: a config carrying an annotation key ran before and now exits with an error, so annotations must move into YAML comments.

  **Test coverage for Instant `Multiply`.** The bundled suite had no case applying a `Multiply` modifier on an `Instant` effect — the one path whose semantics this release corrects elsewhere, where a magnitude of `0` had zeroed the attribute's Base Value and `-0.5` had flipped its sign. The gap was structural rather than incidental: every existing `Multiply` case was durational, so a revert of that correction would have passed the suite clean. The added cases pin the signed-bonus convention, magnitude `0` as the identity, authored order against `Add` in both directions, the subsequent base clamp, and — the discriminating one — that channel grouping does _not_ apply to a Base-Value write: two `+0.5` modifiers sharing a channel on one Instant effect scale independently to ×2.25, where the same two as duration modifiers sum on their channel to ×2.0. That asymmetry is intentional and was previously pinned nowhere. `references/simulation-config.md` documented none of these semantics; it now does, including that a _periodic_ `Multiply` never reaches the base.

  The same audit found three more paths the suite never reached, all now covered: a periodic `Multiply`, which must apply as a flat Current-Value bonus for the effect's lifetime rather than compounding into the base every tick or vanishing entirely — both were live regressions while §5.2's rule was being implemented; `AddPost`, whose placement after the multiply steps is what distinguishes it from `Add`; and `Override`, including §5.3's LIFO tie-break, where an expiring override must fall back to a still-active one rather than to the base. None of the three appeared anywhere in the suite before.

  The suite also gains cases for the reference-graph shapes above. They run under a watchdog rather than an elapsed-time assertion, because an exponential regression does not return at all — a timing check placed after the call never executes, and the suite hangs instead of reporting. The deep-chain case carries a live modifier on the chain's tail: without one, base normalisation has already clamped every attribute before anything reads it, so the case would pin termination at depth while proving nothing about correctness at depth.

  **The suite now runs in CI, and its guarantee is reproducible.** It previously ran nowhere — no workflow referenced anything under `.claude/skills/`, and there was no hook, npm script or pytest config either — which is how an Instant `Multiply` that zeroed a Base Value reached a released artifact. It joins the existing schema-validation job, which already installs the one dependency it needs. `tests/mutate.py` is added alongside it: the suite's real guarantee is that a deliberate defect makes a _named_ case fail, and that was previously asserted in review comments rather than being executable. It carries the two guards that matter — refusing to report a result unless the source actually changed, and treating a crashed run as a caught mutation rather than a survivor, since Python exits `1` for both — plus the three behaviour-preserving mutations that survive by design, each with its reason.

  Three smaller fixes found while reviewing the above: a present-but-empty `attributes:` was accepted as "no attributes" and then crashed the CLI, which reads the raw config where the validated copy has a default; an effect copied from the spec schema reported `missing required 'name'` for its `Name:` key, bypassing the hint that would have explained the casing; and a bound naming an undeclared attribute two or more hops from where resolution started surfaced as a bare `KeyError` rather than a `ConfigError` — unreachable through a parsed config, but reachable by a caller building clamp rules directly.

- 1a3c350: [Fixed] `ugas-schema-author` simulator — four conformance bugs that made simulated attribute traces wrong in ways an author would not notice. Resolves the follow-ups filed while reviewing the modifier-pipeline sweep.

  **Timing was `--timestep`-dependent.** Effect lifetime and tick cadence were tracked with per-step accumulators decremented in the same loop iteration that applied the effect, so an effect was charged for a timestep during which it had only just become active. A `HasDuration` effect lived `duration - timestep`: a 2.0s effect lasted 1.0s at `--timestep 1.0` but 1.5s at `0.5`, meaning the same config produced different answers at different resolutions — the one property a balance-projection tool must not have. The first periodic execution was early for the same reason, and with `execute_on_application: true` and `timestep == period` the effect **double-ticked at t=0**, applying twice the intended magnitude. Scheduling is now absolute (`expire_at`, `next_tick_at`) derived from the authored `apply_at`, and the dead `first_tick_done` field — written twice, never read, which is what let the double-tick through — is gone. Traces are now identical across timesteps.

  **Effect identity was the name string.** Modifier ownership was keyed on the effect's name, and nothing deduped or rejected collisions, so two config entries sharing a name were indistinguishable at removal. The first expiry withdrew _both_ effects' modifiers; a timed effect could permanently strip a same-named `Infinite` effect's contribution. Ownership is now keyed on a per-entry `instance_id`, with the name kept only for display and events.

  **A temporary debuff on a referenced bound permanently destroyed the dependent attribute's Base Value.** Clamping ran as a per-step sweep over every attribute and clamped _Base Values_ against bounds resolved from the referenced attribute's _Current_ Value. With `Health` bounded by `max: MaxHealth`, a 3s `Multiply -0.5` on `MaxHealth` clamped `Health`'s **base** 100 → 50, and `Health` stayed at 50 after the debuff expired — a temporary −50% max-HP debuff permanently halving the character. §5.2 permits Base Values to change only through Instant applications and periodic executions. Base clamping now happens only immediately after such a write and only for the attributes that write touched; Current-Value clamping stays a read-time concern, per §5.3's formula and §5.4's rule that an attribute-reference bound resolves against that attribute's Current Value.

  **Unrecognised operations were silently dropped.** The operation dispatch had no `else` branch and `parse_effects` defaulted a _missing_ `operation` to `Add`, so `Divide`, lowercase `add`, and uppercase `MULTIPLY` all no-opped while the run still logged the effect as applied — and a modifier with no `operation` silently became a flat `Add` nobody authored. §5.2 requires that an implementation MUST NOT silently drop any operation. `operation` is now required and validated case-sensitively, `duration_policy` likewise, and the CLI reports the offending effect and attribute and exits `2` instead of emitting a plausible-looking wrong curve.

  The config is validated more broadly in the same spirit — the first three below previously produced a wrong curve or a hang, the rest a bare traceback:

  - A modifier naming an attribute that was never declared is rejected rather than silently ignored.
  - `period` must be positive. A `period` of `0` used to spin the tick loop forever, as did a negative one; the loop now also fails loudly if a period is too small to advance the schedule at all, which a positive-value check alone does not catch.
  - `period` on an `Instant` effect is rejected as meaningless, and a negative `HasDuration` duration is rejected in favour of `Infinite`.
  - `period`, `duration`, and `apply_at` must be numbers. YAML hands back a string more readily than it looks — `1.0e16` fails PyYAML's float pattern, which requires a signed exponent — and comparing one later raised a bare `TypeError`.
  - A missing effect `name`, or a modifier missing `attribute` or `value`, raises a config error instead of a `KeyError` traceback; a non-numeric modifier `value` is rejected rather than failing later in the arithmetic; a `channel` that is not a string is rejected rather than failing when Multiply modifiers are grouped by it; and a modifier that is not a mapping at all is reported instead of raising `AttributeError`.

  Attributes whose initial value starts outside their declared bounds are normalised once at t=0, before any effect is active — restoring behaviour the old per-step clamp sweep provided incidentally, without reintroducing the write-through it caused.

  Base clamping now runs at write time rather than as a per-step sweep. It is order-sensitive when one attribute's bound references another, so the order is fixed deliberately rather than inherited from clamp-rule declaration order.

  No schema, spec, or gameplay-data changes; this is entirely the bundled simulator plus its config reference.

- 0eeb83c: [Added] Asynchronous-validation lifecycle state for Gameplay Abilities (§8.8), resolving the activation/validation race condition. Introduces an explicit `PendingConfirmation` state in the §8.2 lifecycle, sitting between `Activating (Validating)` and `Commit`, for an activation that has passed the synchronous §8.3 checks but whose authoritative outcome is still outstanding pending asynchronous validation (server-side anti-cheat, remote-inventory check, or premium-consumable entitlement/auth). While in `PendingConfirmation` an activation has NOT committed: no cost or cooldown is consumed, `ActivationOwnedTags` are not granted, and it is not executing authoritative Tasks. Defines two coordinated paths. Path A (server-authoritative, no prediction): a §8.3-passing async ability enters `PendingConfirmation` before Commit; async success proceeds to Commit -> Active, async failure (or timeout) transitions Fail -> `Granted` with nothing consumed. Path B (client-side prediction): the owning client predictively commits and enters a _speculative_ Active carrying a `PredictionKey` (§13.8) while the authoritative server holds `PendingConfirmation` until validation resolves — `ConfirmPrediction(key)` confirms the predicted commit with no visible change; `RejectPrediction(key)` rolls the speculative activation back via the §13.5 reconciliation path (restoring the §13.8.3 `CaptureState()` snapshot) and returns the ability to `Granted`. This gives the late-rejection race a modeled transition instead of an undefined one. Also specifies §8.6 cancellation while pending (no cost/cooldown consumed; in-flight async validation SHOULD be aborted and late results MUST be discarded) and binds a speculative-Active to the §13.8.2 prediction window (a client MUST NOT stay speculatively Active past the window awaiting confirmation). Updates the §8.2 ASCII state diagram to show the new state, the sync-only `Validating -> Commit` bypass, the predicted-Active vs authoritative-pending distinction, and the reject -> rollback -> `Granted` edge.
