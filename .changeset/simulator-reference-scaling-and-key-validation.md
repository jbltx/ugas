[Fixed] `ugas-schema-author` simulator — clamp-bound reference graphs now scale to any legal shape, and a typo in a config key is an error rather than a silently substituted default. Resolves the follow-ups filed while reviewing the clamped-bound change in this same release.

**Bound references resolve iteratively, at any depth or width.** Attribute-reference bounds (`max: MaxHealth`) resolve against the referenced attribute's *clamped* Current Value, which makes resolution a walk over the reference graph rather than a single hop. That walk is iterative and memoised per read: a chain of a thousand references, or a lattice in which many attributes reference a shared set, resolves in near-linear time on a bounded stack. Written recursively — the obvious shape, given §5.4's recursive definition — it would raise an uncaught `RecursionError` past roughly five hundred links, and would enumerate reference *paths* rather than *nodes*, which is exponential: a 20-level lattice took about 13 seconds and a 30-level one never finished, with nothing rejecting either. Both shapes are acyclic and therefore legal, so the cycle rejection does not cover them. The parse-time cycle check is iterative for the same reasons, sharing one visited set across every rule so accepting a wide lattice is linear too, and it still reports the full cycle path. Batch base-clamping orders its writes with a topological sort instead of rescanning for a ready attribute, which was cubic in the number of attributes written — 6 seconds for a thousand — and would otherwise have become the next bottleneck. Deliberately *not* added: a depth or size limit. Nothing recurses on any config-dependent path now, so a limit would reject configs the spec calls legal and that resolve in milliseconds.

**Unknown config keys are rejected at every level.** An unknown key previously meant "take the default", which is the silent-typo class this simulator has been closing progressively: `execute_on_aplication: true` left `execute_on_application` at `false`, so the effect never executed on application while the run still reported it applied — a plausible-looking but wrong curve, with no signal. The same hole existed at the top level, where `efects:` yielded an empty effect list and a flat trace that reads as "your design does nothing"; inside a modifier; and inside the `simulation` block, where `timestap:` silently reverted to the default timestep and changed the whole x-axis. Every mapping the script reads keys out of now has a closed key set.

The messages name the likely cause rather than only the symptom, because the common trigger is copy-paste rather than mistyping: `schemas/gameplay_effect.json` and the genre packs are PascalCase (`DurationPolicy`, `Attribute`, `Magnitude`) and carry fields this simplified format does not model (`Priority`, `Executions`, `GrantedTags`, …), so a config adapted from an entity file arrives with every key unknown. A casing variant of a real key is reported as such, `Magnitude` is pointed at `value`, and spec-only fields are reported as unsupported rather than misspelled. A plain misspelling gets no hint — only the expected-key list.

Malformed shapes now produce a message and exit `2` where they previously raised a traceback and exit `1`: an `effects` block that is not a list, an effect or modifier that is not a mapping, a `modifiers` block that is not a list, a non-mapping `attributes` block, a non-string attribute name, a non-numeric initial value, and an empty config file — which YAML loads as `None`, and which used to fail while reading the `simulation` block, outside the handler that turns a config error into a message. Booleans are rejected wherever a number is required, here as elsewhere, since `bool` is an `int` subclass and `float(True)` is `1.0`, so a YAML `Health: yes` would otherwise become an attribute worth one. **The new rejections are breaking**: a config carrying an annotation key ran before and now exits with an error, so annotations must move into YAML comments.

**Test coverage for Instant `Multiply`.** The bundled suite had no case applying a `Multiply` modifier on an `Instant` effect — the one path whose semantics this release corrects elsewhere, where a magnitude of `0` had zeroed the attribute's Base Value and `-0.5` had flipped its sign. The gap was structural rather than incidental: every existing `Multiply` case was durational, so a revert of that correction would have passed the suite clean. The added cases pin the signed-bonus convention, magnitude `0` as the identity, authored order against `Add` in both directions, the subsequent base clamp, and — the discriminating one — that channel grouping does *not* apply to a Base-Value write: two `+0.5` modifiers sharing a channel on one Instant effect scale independently to ×2.25, where the same two as duration modifiers sum on their channel to ×2.0. That asymmetry is intentional and was previously pinned nowhere. `references/simulation-config.md` documented none of these semantics; it now does, including that a *periodic* `Multiply` never reaches the base.

The suite also gains cases for the reference-graph shapes above. They run under a watchdog rather than an elapsed-time assertion, because an exponential regression does not return at all — a timing check placed after the call never executes, and the suite hangs instead of reporting.
